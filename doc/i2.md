## Comportamento entregue

- CT-08B usa `OperacaoConsumoRepositoryPort.bloquearOperacao`, exatamente o advisory lock transacional do CT-05 (`hashtextextended(operationId, 46841)`). Funciona antes de existir a linha. A identidade global de compensação também é serializada, em namespace distinto (`46842`), antes do lock da operação.
- Header `Idempotency-Key` deve ser UUID não nulo e coincidir com `compensationId`. A tabela `compensacao_estoque` guarda chave única, operação, hash SHA-256 do pedido tipado, pedido/evidência, resultado e horário. A mesma chave/pedido retorna o resultado salvo; outro pedido ou outra operação com a chave gera `409 IDEMPOTENCY_CONFLICT`. Outra chave após `CLOSED`/`REVERSED` também gera conflito.
- Fechamento primeiro grava `CLOSED`, sem materiais/movimentos nem referências fictícias de OS. CT-05 tardio recebe `409 ATTEMPT_CLOSED`, com `operationId` e `compensationId`.
- Consumo primeiro exige `unusedConfirmed=true`, motivo `CANCELLED_BEFORE_USE` ou `VERIFIED_RETURN`, verificador UUID não zero, horário até 30 segundos no futuro e referência não vazia. Não uso pendente gera `409 MATERIAL_USE_NOT_RESOLVED`; conferência ausente/inválida gera `409 EVIDENCE_REQUIRED`. Não há crédito nem fechamento nesses casos. O contrato não fornece um sistema externo de conferência: a evidência é a declaração auditável enviada pela OS.
- Reversão bloqueia materiais na mesma ordem de UUID usada no consumo, credita as quantidades das baixas originais, grava entradas inversas e muda a operação para `REVERSED`, tudo no mesmo commit. `original_movement_id UNIQUE` impede dois retornos para a mesma baixa. A entrada inversa referencia operação, compensação, baixa original e autor da conferência. Os movimentos originais e seus metadados permanecem intactos. CT-05 posterior recebe `409 ATTEMPT_REVERSED`.
- `REJECTED` confirmado permanece recusado, sem crédito. Se CT-08B o encontrar, persiste a solicitação/resultado da resolução e retorna `409 OPERATION_ALREADY_REJECTED` **após commit**. A OS reconfirma pelo CT-08. Se a OS já o consultou, resolve a tentativa diretamente, sem chamar CT-08B.
- CT-08 inclui `operationId`, `compensationId` nos dois estados compensados e listas de movimentos com a forma exigida por `2.0.0-os-baseline.1`: vazias para `CLOSED`/`REJECTED`, não vazias para `CONSUMED`/`REVERSED`. Neste último, devolve somente movimentos inversos. O acesso a CT-08B é exclusivo da identidade OS, com correlação UUID obrigatória.

O hash usa o pedido tipado, de modo que a ordem das propriedades JSON não altera a identidade. Campos adicionais sem significado no contrato não participam do hash. A evidência gravada de uma compensação bem-sucedida não é substituída em retries.

## Persistência

`V4__inventory_compensations.sql` adiciona o registro da compensação e os vínculos inversos, amplia os estados e permite referências de consumo ausentes **somente em CLOSED**. Checks por estado e FKs adiadas garantem que o estado compensado e os movimentos tenham a compensação correspondente no commit. O índice único original por operação/material é substituído por índices separados para baixa e retorno.

V1–V3 permaneceram byte a byte inalteradas. Checksums comparados com o banco local I1: V1 `470359204`, V2 `3489036`, V3 `-1585769654`. V4: `-2068998895`. O banco vazio I2 migrou até V4 com Hibernate `validate`. Não houve acesso ao banco compartilhado.

## Reprodução local

Use Docker Desktop e PowerShell 7. Os nomes/portas abaixo são exclusivos do ensaio I2; para uma nova execução mantenha os bancos anteriores e use nomes/portas livres. Credenciais abaixo pertencem apenas ao PostgreSQL descartável.

No checkout do Inventory:

```powershell
docker run -d --name numberone-i2-postgres -p 127.0.0.1:55482:5432 `
  -e POSTGRES_PASSWORD=i2-local-postgres postgres:17-alpine
docker exec numberone-i2-postgres pg_isready -U postgres
Get-Content scripts/provisionar-i2.sql -Raw |
  docker exec -i numberone-i2-postgres psql -U postgres -v ON_ERROR_STOP=1

$inventoryCheckout = (Get-Location).Path
docker run --rm -v "${inventoryCheckout}:/workspace" -v numberone-i1-maven21:/root/.m2 -w /workspace `
  -e DB_URL=jdbc:postgresql://host.docker.internal:55482/inventory_db `
  -e DB_USERNAME=inventory_i2 -e DB_PASSWORD=i2-local-inventory -e I2_POSTGRES_TEST=true `
  maven:3.9.14-eclipse-temurin-21 bash -lc `
  'cp -r .mvn /tmp/.mvn; sed "s/\r$//" mvnw > /tmp/mvnw; bash /tmp/mvnw -B -ntp test'

# Pare o servidor I2 antes de substituir um jar anterior. Em volume Windows,
# remova apenas o backup gerado pelo repackage se já existir.
if (Test-Path target/inventory-service-0.0.1-SNAPSHOT.jar.original) {
  Remove-Item -LiteralPath target/inventory-service-0.0.1-SNAPSHOT.jar.original
}
docker run --rm -v "${inventoryCheckout}:/workspace" -v numberone-i1-maven21:/root/.m2 -w /workspace `
  maven:3.9.14-eclipse-temurin-21 bash -lc `
  'cp -r .mvn /tmp/.mvn; sed "s/\r$//" mvnw > /tmp/mvnw; bash /tmp/mvnw -B -ntp -DskipTests package'

docker run -d --name numberone-i2-inventory -p 127.0.0.1:18082:8080 `
  -v "${inventoryCheckout}/target:/artifact:ro" `
  -e DB_URL=jdbc:postgresql://host.docker.internal:55482/inventory_db `
  -e DB_USERNAME=inventory_i2 -e DB_PASSWORD=i2-local-inventory `
  -e OS_TO_INVENTORY_TOKEN=i2-local-os-to-inventory `
  -e BILLING_TO_INVENTORY_TOKEN=i2-local-billing-to-inventory -e GATEWAY_HEADERS_TRUSTED=true `
  maven:3.9.14-eclipse-temurin-21 java -jar /artifact/inventory-service-0.0.1-SNAPSHOT.jar

./scripts/validar-i1.ps1 -Base http://127.0.0.1:18082 `
  -OsToken i2-local-os-to-inventory -BillingToken i2-local-billing-to-inventory
```
