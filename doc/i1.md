- Infra de referência. `feature/inventory-db-isolation` em `481f0328c2f19179a4ffb8f33f81a06b151d2785`, consultada em cópia separada. Contrato da OS `2.0.0-os-baseline.1`.

No Inventory, `CatalogoEstoqueService` e `InventoryAdminController` atendem `POST /api/admin/itens`, `GET /api/admin/itens`, `GET /api/admin/itens/{id}`, `POST /api/admin/estoque/entrada` e `GET /api/admin/estoque/itens/{id}/movimentacoes`. O autor da entrada vem da identidade administrativa do Gateway. Saldo inicial positivo registra uma entrada no cadastro.

`InventoryInternalController` atende referência de item, CT-05 e CT-08. `InventoryAccessFilter` separa OS, Billing e ADMIN. O preço de referência usa `preco_venda`, a descrição usa o nome quando o catálogo não tem descrição e a consulta de preços do Billing mantém o corpo existente. As chamadas internas requerem bearer opaco e `X-Correlation-Id` UUID. O Inventory aceita os cabeçalhos de identidade do Gateway apenas com `GATEWAY_HEADERS_TRUSTED=true`. Em ambiente integrado, habilite essa opção na rede privada onde o Gateway remove e reinjeta os cabeçalhos de identidade.

`ConsumirEstoqueService` reaproveita o hash SHA-256 e o lock pessimista do item. Normaliza as linhas por UUID, soma quantidades com limite de `int` e serializa pelo `operationId` com advisory lock transacional. A transação grava o pedido normalizado e, quando há saldo, as baixas e movimentos. A recusa por falta de saldo é gravada antes do HTTP 409. ID de material ausente ou inativo no CT-05 é `400 INVALID_REQUEST`, sem recusa por saldo. O consumidor atual da OS mantém esse caso pendente. CT-08 lê os movimentos persistidos e devolve `404 UNKNOWN` se a operação ainda não estiver visível.

Na OS, o patch altera `HttpSagaParticipants`, `MaterialReferenceConfiguration` e `inventory.openapi.yaml` e acrescenta `HttpMaterialReferenceGateway`, `HttpMaterialReferenceGatewayTest` e `InventoryI1IT`. O provider HTTP usa o mesmo cliente, URL, token e correlação da Saga. A única adição ao OpenAPI é a rota de referência e seu schema. A OS converte o preço para `BigDecimal`, devolve 404 para peça ausente, 409 `MATERIAL_NOT_ACTIVE` para peça inativa e 503 `MATERIAL_REFERENCE_UNAVAILABLE` para falha de transporte, HTTP inesperado ou resposta inválida.

## Banco local e migrations

`V1__create_inventory_schema.sql` e `V2__create_inventory_reservations.sql` são cópias exatas da referência. A V2 permanece no histórico Flyway, com suas tabelas legadas sem uso pelo fluxo I1. A V3 cria as tabelas de operação e associa os movimentos de consumo à operação. A aplicação usa Hibernate `validate`.

Em PowerShell 7, no checkout do Inventory, com Docker local e PostgreSQL dedicado à I1:

```powershell
docker run -d --name numberone-i1-postgres -p 127.0.0.1:55481:5432 `
  -e POSTGRES_PASSWORD=i1-local-postgres postgres:17-alpine
docker exec numberone-i1-postgres pg_isready -U postgres
Get-Content -Raw ./scripts/provisionar-i1.sql |
  docker exec -i numberone-i1-postgres psql -U postgres -v ON_ERROR_STOP=1
```

`inventory_db` usa o proprietário `inventory_i1` e `service_order_db` usa `os_i1`. O provisionamento revoga `CONNECT` de `PUBLIC` nos dois bancos. Confirme com `has_database_privilege` para cada usuário no banco do outro.

## Roteiro local

1. No Inventory, use JDK 21, carregue `.env.example` e execute o Wrapper. As credenciais do exemplo são para o PostgreSQL descartável acima.

   ```powershell
   Get-Content .env.example | Where-Object { $_ -match '^\w+=' } | ForEach-Object {
       $name, $value = $_ -split '=', 2
       Set-Item -Path "Env:$name" -Value $value
   }
   $env:SERVER_ADDRESS = '127.0.0.1'
   .\mvnw.cmd -B -ntp test
   .\mvnw.cmd -B -ntp package
   java -jar target/inventory-service-0.0.1-SNAPSHOT.jar
   ```

2. Em outro terminal, rode o teste HTTP direto no Inventory.

   ```powershell
   ./scripts/validar-i1.ps1
   ```

3. No checkout da OS com o patch, use JDK 25 e um banco descartável vazio da OS. O teste sobe a OS real em uma porta livre e usa as rotas administrativas usuais. O Billing simulado entrega `OrcamentoEnviado` e `OrcamentoAprovado` ao inbox real com as fixtures do contrato. O relay encaminha os requests para o Inventory real e descarta uma resposta confirmada do CT-05 para o teste de recuperação.

   ```powershell
   $env:DB_URL = 'jdbc:postgresql://127.0.0.1:55481/service_order_db'
   $env:DB_USERNAME = 'os_i1'
   $env:DB_PASSWORD = 'i1-local-os'
   $env:I1_INVENTORY_URL = 'http://127.0.0.1:18081'
   $env:OS_TO_INVENTORY_TOKEN = 'i1-local-os-to-inventory'
   .\mvnw.cmd -B -ntp '-Dit.test=InventoryI1IT' '-Djacoco.skip=true' verify
   ```

   Para repetir preservando os dados da execução anterior, crie um schema vazio como `os_i1`, acrescente `?currentSchema=<schema>` ao `DB_URL` e configure `SPRING_FLYWAY_DEFAULT_SCHEMA` com o mesmo nome. Para subir a OS fora do teste, use `APP_MATERIAL_REFERENCE_PROVIDER=http`, `INVENTORY_BASE_URL=http://127.0.0.1:18081` e `OS_TO_INVENTORY_TOKEN`.

Na execução registrada, foram usadas as imagens `maven:3.9.14-eclipse-temurin-21` e `maven:3.9.11-eclipse-temurin-25` como ambientes de JDK. O Maven Wrapper de cada repositório executou `bash mvnw -B -ntp test`, `bash mvnw -B -ntp package` ou `bash mvnw -B -ntp -Dit.test=InventoryI1IT -Djacoco.skip=true verify`, conforme a etapa. O `mvnw` com CRLF foi convertido para LF em uma cópia temporária dentro dos contêineres. Para o teste da OS em Docker Desktop, os hosts de `DB_URL` e `I1_INVENTORY_URL` foram `host.docker.internal`.
